# 05 · 健康检查设计

> 对应文件：`backend/app/api/v1/endpoints/health.py`
> 目标：搞懂为什么健康检查要拆成两个，以及“依赖挂了但进程还活着”该怎么表达。

---

## 1. 两种探针，两种问题

| 探针 | 问的问题 | 挂了怎么办 |
| --- | --- | --- |
| **liveness（存活）** `/healthz` | 你这个进程还活着吗？ | 重启进程 |
| **readiness（就绪）** `/readyz` | 你现在能正常服务吗？ | 暂时不把流量给你，**不重启** |

关键区别在于**编排系统会采取什么动作**。

### 如果混在一起会怎样

假设只有一个 `/healthz`，里面同时 ping 了 MySQL。

- MySQL 挂了 → `/healthz` 返回 500
- Docker / Kubernetes 认为“应用挂了” → **重启应用**
- 应用重启 30 次，MySQL 还是挂的，应用还是起不来
- 结果：数据库故障被放大成“应用也在不停崩溃”，日志被重启记录淹没

数据库挂了，重启 API 进程没有任何意义。**问题不在这个进程。**

所以：

- `/healthz` 只检查自己：进程活着、事件循环没死 → 200
- `/readyz` 才检查依赖：MySQL、Redis → 任一不可用 → 503

## 2. `/healthz`：越简单越好

```python
@router.get("/healthz")
async def healthz() -> dict[str, str]:
    settings = get_settings()
    return {"status": "ok", "version": settings.app_version, "env": settings.app_env}
```

没有 I/O、没有 await、不碰数据库。它唯一的作用是证明：**这个进程还能处理 HTTP 请求**。

返回信息：

- `version`：部署后确认“跑的是不是我刚发的版本”
- `env`：确认“连的是 dev 还是 prod”，避免把测试环境当生产排查

> 生产里 `/healthz` 可能每秒被调用很多次，它必须便宜到可以忽略。

## 3. `/readyz`：并发探测 + 硬超时

```python
PROBE_TIMEOUT_SECONDS = 2.0


async def _check_database() -> None:
    async with engine.connect() as connection:
        await connection.execute(text("SELECT 1"))


async def _check_redis() -> None:
    await ping_redis()


async def _probe(name: str, probe: Awaitable[None]) -> tuple[str, bool, str | None]:
    try:
        await asyncio.wait_for(probe, timeout=PROBE_TIMEOUT_SECONDS)
    except Exception as exc:
        return name, False, f"{type(exc).__name__}: {exc}"[:200]
    return name, True, None
```

### 3.1 为什么用 `SELECT 1`

- 不用查业务表：探针不该依赖表结构，也不该给业务库添压力
- `SELECT 1` 验证的是“能建立连接、能发 SQL、能拿结果”，链条足够完整
- 连接来自连接池，顺带验证池没坏

### 3.2 为什么必须超时

`asyncio.wait_for(probe, timeout=2.0)`：

- MySQL 网络半死（丢包但不拒绝）时，`connect()` 可能挂 30 秒甚至更久
- 探针自己挂住 → 部署系统以为探针超时 → 同样会误判
- 2 秒不返回，就当作不可用，快速失败

**探针的 timeout 必须小于部署侧的 probe timeout**（比如 compose 里 `timeout: 5s`），否则外层先超时，你连错误信息都拿不到。

### 3.3 为什么并发

```python
results = await asyncio.gather(
    _probe("mysql", _check_database()),
    _probe("redis", _check_redis()),
)
```

串行的话，最坏情况是 2s + 2s = 4s，可能超过外层超时。
并发后最坏 2s。两个依赖互不相关，没有理由排队。

注意 `_probe` 里 `except Exception` 把异常吃掉转成 `(False, 原因)`，所以 `gather` 不会因为一个失败就中断另一个。

### 3.4 返回 503 而不是 200

```python
healthy = all(checks.values())
if not healthy:
    response.status_code = 503
    response.headers["Cache-Control"] = "no-store"
```

FastAPI 里注入 `Response` 对象就能改状态码。

为什么是 503（Service Unavailable）而不是 500：

- 500 = 服务器内部错误，通常意味着代码 bug
- 503 = 服务暂时不可用，通常是依赖/过载，**可以重试**
- 负载均衡和监控对这两个码的处理策略不同

`Cache-Control: no-store` 防止中间层缓存“健康”结果——探针结果永远不该被缓存。

### 3.5 返回体带上原因

```json
{
  "status": "degraded",
  "checks": {"mysql": false, "redis": true},
  "errors": {"mysql": "OperationalError: (2003, \"Can't connect to MySQL server ...\")"}
}
```

排障时一眼看出是哪个依赖、什么错。
但注意错误信息截断到 200 字符（`[:200]`）：堆栈太长会撑爆日志，也可能带出内部路径。

## 4. 和部署怎么配合

`deploy/docker-compose.prod.yml`：

```yaml
healthcheck:
  test: ["CMD-SHELL", "python -c \"import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:8000/healthz', timeout=3).status==200 else 1)\""]
  interval: 20s
  timeout: 5s
  retries: 5
```

- 探的是 `/healthz`（容器存活），不是 `/readyz`
- 容器 unhealthy 时，编排层可以选择重启；而 `/readyz` 503 只该影响“要不要导流量”
- 这也是为什么健康检查必须挂**根路径**：部署脚本写死了 `/healthz`，后端改路径就得改部署

本地验证：

```bash
curl -i http://127.0.0.1:8000/healthz
# 200 + x-request-id

curl -i http://127.0.0.1:8000/readyz
# 依赖正常: 200 {"status":"ok","checks":{"mysql":true,"redis":true}}
# 依赖挂掉: 503 {"status":"degraded",...}
```

## 5. 一个实验，建议自己跑一遍

把 `DATABASE_URL` 指到一个不存在的端口，启动服务：

```bash
cd backend
env DATABASE_URL='mysql+asyncmy://seat:x@127.0.0.1:3399/campus_seat' \
    .venv/bin/uvicorn app.main:app --port 8001
```

观察三件事：

1. 进程**正常启动**（说明 import 时没有连库）
2. `/healthz` 仍然 200（进程活着）
3. `/readyz` 返回 503，`errors.mysql` 里有 `Connection refused`

这个实验同时验证了“engine 懒连接”和“探针语义分离”两个设计。

## 6. 踩坑记录

**坑 1：把 DB ping 放进 `/healthz`**
短期看不出问题，线上数据库抖动时会引发重启风暴。

**坑 2：探针没有超时**
依赖半死时探针自己挂住，监控显示“探针超时”，反而掩盖了真实原因。

**坑 3：`/readyz` 返回 200 但 body 说 degraded**
状态码和 body 必须一致。负载均衡只看状态码，body 再详细也没用。

**坑 4：健康检查被缓存**
CDN / 反向代理缓存了 200，依赖挂了还显示健康。所以加 `no-store`。
