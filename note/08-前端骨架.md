# 08 · 前端骨架

> 对应文件：`frontend/vite.config.ts`、`src/main.tsx`、`src/router.tsx`、`src/lib/queryClient.ts`、`src/layouts/*`
> 目标：搞清楚一个 React SPA 从 `npm run dev` 到页面渲染，中间有哪几层。

---

## 1. Vite：开发服务器与构建工具

```ts
// frontend/vite.config.ts
export default defineConfig({
  plugins: [react(), tailwindcss()],
  server: {
    port: 5173,
    proxy: {
      '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true },
    },
  },
  build: { outDir: 'dist', sourcemap: false },
})
```

### 1.1 开发模式 vs 构建

| 命令 | 做什么 |
| --- | --- |
| `npm run dev` | 起 Vite dev server，按需编译，热更新（HMR） |
| `npm run build` | `tsc --noEmit` 类型检查 + Rollup 打包到 `dist/` |
| `npm run typecheck` | 只做类型检查，不产出文件 |

dev 模式不做打包，浏览器请求哪个模块就编译哪个，所以启动是毫秒级。
生产必须构建：浏览器不认 `.tsx`，也不该加载几千个源文件。

### 1.2 `/api` 代理解决跨域

开发时前端在 `5173`，后端在 `8000`，直接请求就是跨域。

```ts
proxy: { '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true } }
```

浏览器请求 `http://localhost:5173/api/v1/...`，Vite 转发给 `8000`，浏览器看到的始终是同源。
生产环境由 Caddy 做同样的转发（`handle /api/* { reverse_proxy api:8000 }`），前端代码不用改。

### 1.3 为什么不用 Next.js

这个项目**登录后才有内容**，没有 SEO 需求，不需要 SSR。
用 Vite 少一个 Node 进程、少一套服务端渲染的心智负担。

## 2. React 入口

```tsx
// src/main.tsx
const container = document.getElementById('root')
if (!container) {
  throw new Error('#root 不存在，检查 index.html')
}

createRoot(container).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <RouterProvider router={router} />
    </QueryClientProvider>
  </StrictMode>,
)
```

三层 Provider，顺序有讲究：

```
StrictMode           开发期检查（重复渲染、废弃 API 警告）
  QueryClientProvider 提供请求缓存
    RouterProvider    提供路由
```

`QueryClientProvider` 必须在 `RouterProvider` 外层：路由里的页面组件会用到 `useQuery`，Provider 要在它们之上。

### 2.1 `createRoot` 取代 `ReactDOM.render`

React 18 起的新入口。`document.getElementById("root")` 可能返回 `null`，所以先判空再 mount——否则 TypeScript 会报 `container` 可能为 null。

### 2.2 StrictMode 为什么会让 effect 跑两次

开发模式下，StrictMode 会故意把组件挂载 → 卸载 → 再挂载，用来暴露“没有正确清理的副作用”。

- 只在 **dev** 生效，生产构建不会
- 看到接口请求两次，先别慌，确认是 StrictMode 还是真的重复调用

## 3. 路由：一个工程，两套布局

```tsx
// src/router.tsx
export const router = createBrowserRouter([
  {
    element: <AuthLayout />,
    children: [
      { path: '/login', element: <Login /> },
      { path: '/register', element: <Register /> },
    ],
  },
  {
    element: <UserLayout />,
    children: [
      { index: true, element: <Home /> },
      { path: '/rooms', element: <Rooms /> },
    ],
  },
  {
    element: <AdminLayout />,
    children: [{ path: '/admin', element: <Dashboard /> }],
  },
  { path: '*', element: <NotFound /> },
])
```

### 3.1 嵌套路由与 `<Outlet />`

父路由只写 `element`，不写 `path`；子路由匹配后，渲染在父组件的 `<Outlet />` 位置。

```tsx
export function UserLayout() {
  return (
    <div>
      <header>...</header>
      <main><Outlet /></main>     {/* ← /rooms 或首页渲染在这里 */}
      <footer>...</footer>
    </div>
  )
}
```

好处：布局只写一次，切换页面时顶栏/侧栏不重新挂载，状态不丢。

### 3.2 `index: true`

表示“父路径的默认子路由”。`/` 匹配 `Home`，而不是去匹配一个叫空字符串的路由。

### 3.3 `NavLink` 的 `isActive`

```tsx
<NavLink
  to="/rooms"
  className={({ isActive }) => isActive ? 'bg-slate-900 text-white' : 'text-slate-600' }
>
```

`NavLink` 比 `Link` 多知道“当前是否激活”，用来做导航高亮。
`end` 属性控制是否精确匹配：`to="/"` 加 `end`，否则所有路径都会把首页点亮。

### 3.4 `path: '*'` 兜底

任何没匹配上的路径 → 404 页。没有它，用户输错地址会看到一片空白。

### 3.5 路由守卫为什么还没接

`RequireAuth` 在 M0 是占位。原因：它依赖登录态（Zustand store），而 store 是 M1-15 的活。

**顺序反了会返工**：先写守卫再写登录，守卫只能写个假的 `return children`，等于没写。

M1 完成后的形态：

```tsx
{
  element: <RequireAuth roles={['admin']}><AdminLayout /></RequireAuth>,
  children: [...]
}
```

> 记住：前端路由守卫只是**体验**，真正的权限永远在后端校验。改 URL 绕过守卫很容易，绕过后端 403 才是真安全。

## 4. TanStack Query：服务端状态归它管

```ts
// src/lib/queryClient.ts
export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      retry: 1,
      staleTime: 30_000,
      refetchOnWindowFocus: false,
    },
    mutations: { retry: 0 },
  },
})
```

### 4.1 它解决什么问题

手写请求要自己管：loading、error、缓存、重试、失效、并发去重。
TanStack Query 把这些标准化：

```tsx
const { data, isLoading, error } = useQuery({
  queryKey: ['rooms', buildingId],
  queryFn: () => api.get(`/rooms?building=${buildingId}`),
})
```

同一个 `queryKey` 的请求会自动去重、缓存、共享。

### 4.2 三个默认值为什么这么设

| 配置 | 值 | 理由 |
| --- | --- | --- |
| `retry: 1` | 只重试一次 | 4xx 重试没意义，还会放大故障 |
| `staleTime: 30_000` | 30 秒内视为新鲜 | 座位图不需要每次聚焦都重查 |
| `refetchOnWindowFocus: false` | 切回标签页不自动刷 | 抢座时窗口切换可能触发请求突增 |
| `mutations.retry: 0` | 写操作不自动重试 | 预约/取消不是幂等的，重试可能重复下单 |

最后一条尤其重要：**写请求默认不能重试**，除非接口支持 `Idempotency-Key`。

## 5. Tailwind CSS 4

```css
/* src/styles/index.css */
@import "tailwindcss";

body {
  margin: 0;
  @apply bg-slate-50 text-slate-900 antialiased;
}
```

```ts
// vite.config.ts
plugins: [react(), tailwindcss()]
```

Tailwind 4 的变化：

- 不再需要 `tailwind.config.js`（默认扫描项目文件）
- 用 `@tailwindcss/vite` 插件，而不是 PostCSS 配置
- CSS 入口写 `@import "tailwindcss"`，不是三条 `@tailwind` 指令

写法就是堆类名：

```tsx
<div className="rounded-xl border border-slate-200 bg-white p-6 shadow-sm">
```

优点是不用起类名、不用在 CSS 和 TSX 之间跳；缺点是 JSX 会变长。
本项目约定：**页面“能用”优先，不做动画/暗色/复杂响应式**，避免前端拖进度。

## 6. 生产部署时的前端

```yaml
# deploy/Caddyfile
handle {
  root * /srv
  try_files {path} /index.html
  file_server
}
```

`try_files` 是 SPA 的关键：`/rooms` 这个路径服务器上并没有对应文件，必须回退到 `index.html`，再由前端路由接管。

- 开发：Vite dev server 自带 history fallback
- 生产：Caddy 配 `try_files`，否则刷新页面就 404

前端构建产物是纯静态文件，由 Caddy 直接托管，**不需要跑 Node 进程**。

## 7. 踩坑记录

**坑 1：`localhost` 和 `127.0.0.1` 不是一回事**
Vite 默认可能只监听 `::1`（IPv6），`curl 127.0.0.1:5173` 会连不上。用 `--host 127.0.0.1` 或访问 `localhost`。

**坑 2：`npm run build` 先跑 `tsc --noEmit`**
类型错误会直接让构建失败。这是好事——CI 里能拦住，别把 `tsc` 从 build 脚本里删掉。

**坑 3：`noUnusedLocals: true`**
`tsconfig` 开了未使用变量检查，`import` 了没用会报错。删 import 别手软。

**坑 4：Tailwind 类名拼错不报错**
`bg-slate-50` 写成 `bg-slate-500` 不会报错，只是颜色不对。改完样式一定看一眼页面。
