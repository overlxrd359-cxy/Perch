# 04 · 结构化日志与请求 ID

> 对应文件：`backend/app/core/logging.py`、`backend/app/middleware/request_id.py`
> 目标：线上出问题时，能用一条日志把整个请求串起来。

---

## 1. 为什么不用 `print`

`print` 的问题不是“low”，而是**没有结构**：

```
用户 123 预约座位 45 失败
```

出问题时你想查“哪个请求、什么时间、耗时多少、用户是谁”，只能靠字符串匹配，还容易被日志内容里的空格/中文搞乱。

结构化日志是**一行一个 JSON**：

```json
{"ts":"2026-11-15T14:50:43.375+00:00","level":"INFO","logger":"app.access","msg":"request completed","request_id":"6f8d7abc9c224d88ade153f0b81e7407","duration_ms":0.15,"path":"/nope","status":404,"method":"GET"}
```

好处：

- 日志系统（Loki / ELK / CloudWatch）能按字段检索：`status=500 AND path="/api/v1/reservations"`
- 不用写正则解析
- 一条日志自带上下文，不用去别处拼

## 2. Python logging 的三个角色

```
Logger     →  产生日志（logging.getLogger("app.access")）
Handler    →  决定去哪（stdout / 文件 / 网络）
Formatter  →  决定长什么样（纯文本 / JSON）
```

层级关系：`app.access` 的父 logger 是 `app`，再往上是 `root`。子 logger 默认把日志往上传（`propagate=True`），最终由 root 的 handler 输出。

所以 `setup_logging()` 只配置 root 一次，全项目生效。

### 2.1 幂等初始化

```python
_configured = False

def setup_logging(*, level: str | int = "INFO", json_output: bool = True) -> None:
    global _configured
    if _configured:
        return

    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(JsonFormatter() if json_output else logging.Formatter(...))

    root = logging.getLogger()
    root.handlers.clear()
    root.addHandler(handler)
    root.setLevel(level)
    ...
    _configured = True
```

为什么要幂等：`uvicorn --reload` 会重新 import 模块，测试里也可能多次 `create_app()`。不防重，日志会变成每条打印 N 遍。

`root.handlers.clear()` 是防“别人先配了一个 handler”，比如 uvicorn 自带的。清掉再装自己的，保证格式统一。

### 2.2 第三方库降噪

```python
_NOISY_LOGGERS = {
    "asyncio": logging.INFO,
    "uvicorn.access": logging.WARNING,
    "sqlalchemy.engine": logging.WARNING,
    "alembic": logging.WARNING,
    "httpx": logging.WARNING,
    "redis": logging.WARNING,
}
```

- `uvicorn.access` 设成 WARNING 等于**关掉它自带的访问日志**，否则每个请求会打两行：一行纯文本、一行我们的 JSON
- `sqlalchemy.engine` 是 SQL echo，DEBUG 模式下会把每条 SQL 和参数刷出来（还可能带敏感数据），需要时再单独开
- `asyncio` 在 DEBUG 下会打印 `Using selector: KqueueSelector` 这种噪音

## 3. JsonFormatter：一条日志怎么组装

```python
class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        payload: dict[str, Any] = {
            "ts": datetime.fromtimestamp(record.created, UTC).isoformat(timespec="milliseconds"),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
            "request_id": request_id_ctx.get(),
        }

        context_user = user_id_ctx.get()
        if context_user is not None:
            payload["user_id"] = context_user

        for key in _EXTRA_WHITELIST:
            if key in record.__dict__ and key not in payload:
                payload[key] = record.__dict__[key]

        if record.exc_info:
            payload["exc"] = self.formatException(record.exc_info)

        return json.dumps(payload, ensure_ascii=False, default=str)
```

逐点解释：

| 代码 | 作用 |
| --- | --- |
| `record.created` | 日志产生的时间戳（float 秒） |
| `fromtimestamp(..., UTC)` | 统一转 UTC；本地时区展示交给前端/日志系统 |
| `request_id_ctx.get()` | 从上下文里拿当前请求 ID，业务代码不用传参 |
| 白名单循环 | 只允许已知字段透传，防止有人 `extra={"password": ...}` 把密码写进日志 |
| `formatException` | 异常堆栈单独放 `exc` 字段，保持 JSON 单行 |
| `ensure_ascii=False` | 中文不转成 `\u4e2d\u6587`，日志可读 |
| `default=str` | 兜底：塞进来的对象转成字符串，不让 `json.dumps` 崩 |

### 为什么要有白名单

```python
_EXTRA_WHITELIST = frozenset(
    {"method", "path", "status", "duration_ms", "user_id", "seat_id", "reservation_id"}
)
```

没白名单的话，任何 `logger.info("x", extra={"anything": obj})` 都会进日志。
而“把整个请求体打出来”是泄露密码/token 的头号原因。白名单让这件事**必须显式申请**，加字段时你会想一下“这个能不能记”。

## 4. ContextVar：请求 ID 怎么跨函数传

### 4.1 问题

路由 → service → repository，调用链可能有 5 层。如果靠参数传 `request_id`，每个函数签名都要加一个参数，蠢且容易漏。

### 4.2 方案：上下文变量

```python
from contextvars import ContextVar

request_id_ctx: ContextVar[str] = ContextVar("request_id", default="-")
user_id_ctx: ContextVar[int | None] = ContextVar("user_id", default=None)
```

用法只有三个操作：

```python
token = request_id_ctx.set("abc123")   # 设置，拿到“恢复令牌”
request_id_ctx.get()                    # 任意位置读取，默认 "-"
request_id_ctx.reset(token)             # 恢复成设置前的值
```

### 4.3 为什么不用全局变量 / thread-local

- 全局变量：并发请求会互相覆盖，A 的日志带上 B 的 ID
- `threading.local()`：只对线程有效。asyncio 里成百上千个协程跑在**同一个线程**上，照样串

`ContextVar` 是 asyncio 原生的：每个 task 有独立的上下文副本，`await` 切换时自动跟着走。

### 4.4 reset 为什么重要

```python
finally:
    request_id_ctx.reset(token)
```

不 reset 的后果：同一个线程/协程池复用后，下一个请求可能继承上一个请求的 ID。
**日志看起来“串号”，排查时会怀疑人生。** 用 `finally` 保证异常路径也恢复。

## 5. 中间件：一个请求的完整生命周期

```python
class RequestIdMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        request_id = _resolve_request_id(request.headers.get("x-request-id"))
        token = request_id_ctx.set(request_id)
        started = time.perf_counter()

        try:
            response = await call_next(request)
        except Exception:
            logger.exception("request failed", extra={...})
            raise
        else:
            response.headers["X-Request-ID"] = request_id
            logger.info("request completed", extra={...})
            return response
        finally:
            request_id_ctx.reset(token)
```

顺序很重要：

1. **先 set**：后续所有日志（包括 CORS/异常处理里的）都带 ID
2. **再 call_next**：真正执行路由
3. **成功时**写响应头 + 访问日志
4. **异常时**记一条失败日志，然后原样抛出（交给异常 handler）
5. **finally reset**：无论成败都恢复上下文

### 5.1 为什么要校验上游传的 ID

```python
_REQUEST_ID_PATTERN = re.compile(r"^[A-Za-z0-9._-]{1,64}$")

def _resolve_request_id(header_value: str | None) -> str:
    if header_value and _REQUEST_ID_PATTERN.fullmatch(header_value):
        return header_value
    return uuid4().hex
```

如果直接信任 `X-Request-ID`，攻击者可以传：

- 超长字符串 → 日志爆炸
- 带 `\r\n` 的内容 → **日志注入**，伪造日志行
- 带 ANSI 转义 → 终端显示错乱

限制字符集和长度，不合法就重新生成。这是“所有外部输入都不可信”的最小实践。

### 5.2 访问日志记什么

```python
logger.info("request completed", extra={
    "method": request.method,
    "path": request.url.path,
    "status": response.status_code,
    "duration_ms": round((time.perf_counter() - started) * 1000, 2),
})
```

只记白名单字段：方法、路径、状态、耗时。
**不记 query string、不记 body、不记 header**——它们最可能含密码、token、身份证号。

`time.perf_counter()` 而不是 `time.time()`：前者是单调时钟，不受系统改时间影响，适合测耗时。

## 6. 踩坑记录

**坑 1：日志打两遍**
uvicorn 默认有自己的 access log。不关掉就会一行纯文本 + 一行 JSON。解法：把 `uvicorn.access` 调到 WARNING，并用 `--no-access-log` 启动（Makefile 里没加，因为已经用 logger 级别压住了）。

**坑 2：异常日志把 JSON 撑成多行**
`json.dumps` 遇到换行会转义成 `\n`，不会真的换行。但如果手动 `logger.info(f"{exc}")`，多行字符串会直接破坏“一行一条”的约定。异常一律走 `exc_info` / `formatException`。

**坑 3：测试里看不到日志**
`setup_logging` 是幂等的，测试进程里第一次配置后不再变。想调整测试日志级别，用 `caplog` fixture，别去改全局状态。

**坑 4：request_id 显示 "-"**
说明日志产生在中间件 set 之前，或者 `reset` 之后。典型场景：`lifespan` 里的启动日志——那时还没有请求，显示 `-` 是对的。
